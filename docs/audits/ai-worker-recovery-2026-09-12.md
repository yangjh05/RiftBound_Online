# AI 워커 복구와 High 우선순위 적용

2026-09-12, 실행 폴더 `data/ai/retrain-run-c-20260905-051719`.

## 원인과 변경

메모리 부족으로 종료를 예약한 워커가 긴 게임을 처리하고 있으면,
여유 메모리가 회복돼도 `retiringProcesses === 0` 조건 때문에 증설이
막혔습니다. 실제로 약 11 GiB가 남았는데 목표 워커 수는 1,
실행 중인 워커는 5에 머물렀습니다.

- 메모리 여유와 대기 작업을 확인한 뒤, 아직 종료 신호를 보내지 않은
  작업 중 워커의 종료 예약을 하나씩 취소합니다.
- 기존 워커를 유지한 다음 필요하면 새 워커를 생성합니다.
- 최대 16개, 메모리 예비량과 관측 RSS에 따른 추가 여유,
  연속 정상 관측 및 증설 간격을 유지합니다.
- 시작 개수가 상한과 같은 풀도 일시적인 감축 후 복구할 수 있습니다.
- 진행 기록에 종료 예약 수, 취소 가능한 예약 수와
  `memory-recovery-v2` 표시를 추가했습니다.

현재 학습의 Windows 프로세스 우선순위는 `High`로 설정했습니다.
해당 실행의 `launch.json`에 `RIFTBOUND_AI_PROCESS_PRIORITY=high`와
`ai-training-priority.cjs` 사전 로드를 저장했습니다. 현재 부모와 풀의
자식 생성 환경에도 적용하여 이후 생성하는 학습 프로세스가 이를 받습니다.

## 검증과 실행 적용

- 집중 테스트 3개와 기존 워커 회귀 테스트 6개 통과.
- 메모리 부족과 회복을 실제 자식 프로세스로 재현했습니다. 첫 게임이
  끝나기 전에 같은 PID와 게임 좌표를 유지하며 종료 예약이 해제됐습니다.
- 우선순위 사전 로드는 별도의 자식과 그 자식 프로세스에서 모두
  Windows High에 해당하는 값 `-14`로 확인했습니다.
- 실행 중 모듈 전체 교체는 활성 비동기 함수 때문에 거부됐으므로
  실학습에서는 이 방법을 사용하지 않았습니다. 별도 실행에서 검증한
  함수 교체를 적용해 현재 풀의 상태를 보존하고, 다음 풀 생성 함수도
  함께 갱신했습니다. 기존 실행과 다음 풀에서 총 16개 테스트 작업이
  정상 완료됐습니다.
- 실제 평가 프로세스 35500과 학습 부모 30148에 적용했습니다.
  기존 워커를 종료하거나 게임을 다시 시작하지 않았습니다.
- 적용 전후 확정 자료 1,551게임과 학습 모델 파일 해시가 유지됐습니다.
  엔진 지문은 `sha256:2d7d82283e9825597f91fb6ed7c57b949d6408e7d460cdfc1a733a715a84c8ba`입니다.
- 적용에 사용한 로컬 디버거 연결과 수신 포트는 작업 후 닫았습니다.

변경 전 소스, 테스트 결과, 적용 기록은
